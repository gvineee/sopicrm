# ODA CRM — პლატფორმის აუდიტი

თარიღი: 2026-09-21. წყარო: ამ სამუშაო საქაღალდის მიმდინარე კოდი, მათ შორის დაუკომიტებელი ცვლილებები. შემოწმება დაიწყო 2026-09-20-ს.

ეს არის რეპოზიტორიის, ძირითადი ბიზნესნაკადებისა და ავტომატური შემოწმებების ანგარიში. ამ აუდიტში ბრაუზერით ყველა გვერდი და რეალური XPass არ შემოწმებულა. დოკუმენტაციაში აღწერილი ძველი hardware ტესტები მიმდინარე სესიაში განმეორებულ დადასტურებად არ ითვლება. პროგრამის ბიზნესკოდი არ შეცვლილა; შემოწმებამ განაახლა გენერირებული build და გამოიყენა სატესტო ბაზა.

ბრაუზერის ხელმისაწვდომობაც შემოწმდა: მიმდინარე სესიაში დაბრუნდა `apps: [], browsers: []`. ამიტომ ამ ანგარიშის UI მიგნებები ეყრდნობა გვერდების კოდს, routes-სა და resources-ს, არა ბრაუზერით გავლილ end-to-end სესიას.

## მთავარი დასკვნა

პლატფორმას აქვს მნიშვნელოვანი მოქმედი საფუძველი: Laravel 13, Vue/Inertia, კომპანიები, თანამშრომლები, პროექტები, დავალებები, აღრიცხვა, ტაბელები, სახელფასო ოპერაციები და კონტრაქტორები. თუმცა პროდუქტი ჯერ არ არის სრულად ინტეგრირებული და საწარმოო მზადყოფნა არ დასტურდება. რამდენიმე ყოველდღიურად საჭირო ეკრანი დემოა ან აკლია; ცალკეული წარმატებული მოდულის ტესტი სრულ მომხმარებლურ პროცესს ვერ ანაცვლებს.

მომხმარებლის უახლესი მიმართულება: BioStar დარჩეს მოწყობილობების მენეჯერად; დასწრებისა და ფინანსური აღრიცხვის პასუხისმგებლობა გადავიდეს CRM-ზე. ამ ანგარიშის პრიორიტეტები ამ მიმართულებას ეყრდნობა. ტექნიკური ინტეგრაციის რეჟიმი ჯერ არ შეცვლილა.

## 3. პრიორიტეტული მიგნებები

ქვემოთ მოცემული ქცევები დადასტურებულია კოდის წაკითხვით; ცალკე მითითებული რისკები ამ სესიაში რეალური მომხმარებლების მონაცემებით არ გამეორებულა.

### A. ადმინისტრირება და მონაცემების ხილვადობა

**A1 — სრული ადმინისტრატორი ელფოსტაზეა მიბმული.** `app/Providers/AppServiceProvider.php:31`-ის `Gate::before()` ნებისმიერი ability-სთვის აბრუნებს `true`-ს, თუ email არის `admin@protect.ge`. ეს თქვენს მოთხოვნილ სრულ წვდომას იძლევა, მაგრამ ასევე გადის ყველა Gate-based შეზღუდვაზე, მათ შორის ფინანსური წვდომის 2FA Gate-ზე. ეს თავისთავად PostgreSQL RLS-ს არ აუქმებს. საჭიროა ცალკე, კონტროლირებადი platform-admin უფლება, აღრიცხული მინიჭებით, MFA-ით და ორგანიზაციის კონტექსტით; პარალელურად ორგანიზაციის owner/admin როლები.

Read-only არჩევანისას CRM-ში თანამშრომლის გათავისუფლება BioStar-ის ბარათს ავტომატურად ვერ გააუქმებს. დასამატებელია პასუხისმგებელი ოპერატორისთვის დავალება, გაუქმების ვადა/გაფრთხილება და BioStar-იდან დადასტურებული შედეგი. სურვილის შემთხვევაში მოგვიანებით შეიძლება კონკრეტული write ოპერაციების დამატება ერთი პასუხისმგებელი სისტემის მკაფიო წესით.

## 5. ადმინისტრატორის დასრულებული მოდული

მოსაწყობია ერთი გასაგები „ადმინისტრირება“ განყოფილება:

1. მომხმარებლები: შექმნა/მოწვევა, თანამშრომელთან მიბმა, აქტივაცია/დეაქტივაცია, სესიები, MFA მდგომარეობა.
2. როლები და ფუნქციათა ჯგუფები: მფლობელი, ტექნიკური ადმინი, HR, ფინანსისტი, პროექტის მენეჯერი, ბრიგადირი, საწყობი, მუშაკი; tenant-specific მორგებადი როლები.
3. უფლებების მატრიცა: ნახვა, შექმნა, შეცვლა, დამტკიცება, ექსპორტი და მგრძნობიარე ველები; scope — საკუთარი, გუნდი, პროექტი, კომპანია, ორგანიზაცია. UI იმავე გადაწყვეტილებას იყენებს, რასაც სერვერი.
4. ეფექტური უფლებების ახსნა: „რატომ აქვს/არ აქვს ეს უფლება?“; როლის, ინდივიდუალური გამონაკლისისა და scope-ის გამჭვირვალე შედეგი. ადმინისტრატორის დანიშვნა ვერ უნდა შეძლოს ჩვეულებრივმა როლის რედაქტორმა.
5. კომპანიები/ობიექტები/წევრობა: ერთიანი არჩევა, კავშირის ვალიდაცია და პასუხისმგებელი პირები.
6. ინტეგრაციები: BioStar კავშირის ჯანმრთელობა, აღმოჩენილი მოწყობილობები, დაუმთხვეველი მომხმარებლები, იმპორტის ბოლო წარმატება, დაგროვილი ისტორია და შეცდომები.
7. Audit: ავტორი, მოქმედება, ჩანაწერი, დრო, ცვლილება და ფილტრები; secrets-ის გარეშე.
8. ბიზნესპარამეტრები: timezone, სამუშაო კვირა, ცვლები/შესვენება, დამტკიცების წესები, ვალუტა და შეტყობინებები.

## 6. ეტაპობრივი სამუშაო გეგმა

ეს არის დამოკიდებულებების რიგი და არა კალენდარული ვადის დაპირება.

**პირველი ეტაპი — არსებული ფუნქციების სისწორე.** PHPStan; პროექტისა და დავალების scope; ადმინისტრატორის მდგრადი იდენტობა; უარყოფილი event/ბარათის გადაცემის ისტორია; გადახდის idempotency/currency/ownership. მიღება: მიზნობრივი regression ტესტები და ყველა არსებული check წარმატებულია.

**მეორე ეტაპი — BioStar → დასწრება.** სერვერზე enforced read-only რეჟიმი; explicit employee/device/card mapping; სრული pagination/checkpoint; event შედეგების კლასიფიკაცია; outage catch-up; დაგეგმილი tenant-aware დამუშავება. მიღება: ცნობილი IN/OUT → სწორი თანამშრომელი → სწორი სესია; განმეორებითი იმპორტი არ აორმაგებს; გათიშვის ისტორია სრულად აღდგება.

**მესამე ეტაპი — ადმინი და მუშაკი.** Admin მოდული; რეალური My Day; ფოტო preview/download; worker submit → manager accept; დღიური ჟურნალის გვერდები; გლობალური ძიება. მიღება: მუშაკი ტელეფონიდან იღებს დავალებას, ამატებს ფოტოს, აგზავნის და ხედავს ნამდვილ შედეგს; მენეჯერი ხსნის ფოტოს და იღებს/აბრუნებს.

**მეოთხე ეტაპი — ტაბელი/ფინანსები/რეპორტები.** ცვლა/ღამის საათები/გადასვლა თარიღზე, დამტკიცება/ჩაკეტვა, დაგვიანებული მოვლენის კორექტირება, export, მფლობელის dashboard. ფორმულებს სჭირდება კომპანიის შეთანხმებული პოლიტიკა; მიმდინარე ანგარიში ბუღალტრულ/საგადასახადო შესაბამისობას არ ადასტურებს.

**მეხუთე ეტაპი — აქტივები და შეტყობინებები.** ხელსაწყოს გაცემა/დაბრუნება/გადაცემა/შეკეთება/ინვენტარიზაცია, immutable movement history; შეტყობინებების ცენტრი და Telegram რეპორტები. მიღება: ერთი ხელსაწყო ერთდროულად ორჯერ არ გაიცემა; დაბრუნებას აქვს სრული ისტორია; შეტყობინება არ დუბლირდება.

**მეექვსე ეტაპი — production მიღება.** Ubuntu deployment, რეგულარული backup და რეალური restore, worker monitoring, დატვირთვის შემოწმება, Android/iPhone, non-admin როლები, სესიების/ავტორიზაციის რეგრესიები და ფაილების დაცვის შემოწმება.

შემდგომი ბიზნესგაფართოება: მასალების მარაგი/საწყობები, შესყიდვები, BOQ და პროექტის გეგმა/ფაქტი, ხარისხი/უსაფრთხოება, ნახაზების რევიზიები/RFI, კლიენტის პორტალი და გაყიდვების CRM. მათი ერთდროული დამატება მიმდინარე ძირითადი პროცესების დამთავრებას გაართულებს.

## 7. Telegram მფლობელისთვის

პირველ ვერსიაში მხოლოდ read-only რეპორტები: დღიური დასწრება, გამონაკლისები, დაგვიანებული დავალებები, მისაღები სამუშაოები, გათიშული reader-ები/ჩამორჩენილი იმპორტი და უფლებებით ნებადართული ფინანსური შეჯამება. ანგარიშის დაკავშირება ერთჯერადი კოდით ავტორიზებული CRM სესიიდან; chat ID ცალკე დამტკიცებული ბმულით. ყოველი გაგზავნისას ხელახლა შემოწმდეს უფლებები, როლის გაუქმებისას გაგზავნა შეწყდეს. შეტყობინებაში უმჯობესია მოკლე შეჯამება და ავტორიზებულ გვერდზე ბმული. ბოტის token ინახება secret store-ში. პირველ ვერსიაში remote door open/ხელფასის დამტკიცების ბრძანებები საჭირო არ არის.

## 8. გადაცემა Claude Code-სთვის

დაიწყოს A2/A3, B1–B5 და C1/C2 მიგნებებით; ამ პროცესების დასრულებამდე სისტემას არ ეწოდოს სრულად გამართული. თითოეული ბილეთი უნდა შეიცავდეს კონკრეტულ trigger-ს, მოსალოდნელ შედეგს, დადასტურების ტესტს და ცვლილების scope-ს. ადმინისტრატორის შემთხვევაში წარმატებული მოქმედება საკმარისი არ არის — იგივე ეკრანი შემოწმდეს ჩვეულებრივი თანამშრომლისა და დელეგირებული მენეჯერის ანგარიშებითაც.
