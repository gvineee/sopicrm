# Claude Code — ODA CRM-ის დასრულებისა და გასწორების ინსტრუქცია

თარიღი: 2026-09-21. ეს ფაილი გადასაცემი ტექნიკური დავალებაა და არა უკვე შესრულებული სამუშაოების ანგარიში.

## მიზანი და არსებული მდგომარეობა

გაასწორე არსებული CRM და ეტაპობრივად მიიყვანე ერთიან, ქართულენოვან, ადვილად გამოსაყენებელ პლატფორმამდე. მუშაკმა ტელეფონიდან მარტივად უნდა მიიღოს დავალება, დაიწყოს, დაამატოს ფოტო/კომენტარი და წარადგინოს; მენეჯერმა შეამოწმოს და მიიღოს/დააბრუნოს; ადმინისტრატორმა მართოს მომხმარებლები, ფუნქციები და მონაცემთა ხილვადობა.

წაიკითხე `docs/platform-audit-2026-09-21.md`, `docs/agent-handoff.md`, არსებული spec და შესაბამისი მოდულების კოდი. აუდიტისას: 142 PHP ტესტი გავიდა, 2 გამოტოვებულია; Node connector 13/13; TypeScript/Pint/build წარმატებულია; PHPStan-ს 9 შეცდომა აქვს. ეს არის საწყისი მაჩვენებლები, მიმდინარე მდგომარეობა თავიდან გადაამოწმე.

არჩეული მიმართულება: BioStar მართავს მოწყობილობებს, ბარათებსა და კარზე დაშვებას. CRM მართავს თანამშრომლებს, სამუშაო დავალებებს, BioStar მოვლენების ასლს, დასწრებას, ტაბელებს, ანაზღაურებასა და ბიზნესანგარიშებს. პირველი ინტეგრაციის ეტაპი read-only-ა. BioStar-ის ლიცენზიის ფასი ამ დავალებაში დადასტურებული არ არის; გადახედე ზუსტ დაყენებულ პროდუქტს და მიმდინარე ოფიციალურ API პირობებს.

მომხმარებლის დამატებითი სავალდებულო მოთხოვნა: ტაბელს ჰქონდეს ელფოსტით გაგზავნა როგორც სათითაოდ, ისე მონიშნული ტაბელების ჯგუფისთვის. განსახილველად წარდგენა და ელფოსტით გაგზავნა სხვადასხვა მოქმედებებია.

## შესრულების წესები

- ჯერ შეამოწმე `git status`/diff და მოქმედი ფაილები. სამუშაო ხეში ბევრი დაუკომიტებელი ცვლილებაა; არ გადაწერო ისინი.
- გაფართოვდეს არსებული მოდელები/ტაბელები. არ შექმნა მეორე Employee, Company, Site, Timesheet ან დამოუკიდებელი ბიზნესლოგიკა მობილურისთვის.
- მომხმარებლის მოთხოვნის ფარგლებში განახორციელე ნაბიჯები და შეამოწმე შედეგი; მხოლოდ გეგმის წერით არ დაასრულო განხორციელების დავალება.
- ცვლილებები იყოს მცირე სამუშაოებად დაყოფილი. ყოველი მნიშვნელოვანი ეტაპი და კონტრაქტის ცვლილება ჩაიწეროს handoff-ში.
- საწარმოო/სამუშაო ბაზაზე `migrate:fresh`, მონაცემების reset და device bulk reset არ გამოიყენო. Migration-ები ინახავს არსებულ მონაცემებს.
- UI-ზე ღილაკის დამალვა არასაკმარისია: იგივე უფლება, ჩანაწერის კუთვნილება და მოქმედების დაშვებული მდგომარეობა სერვერზეც შეამოწმე.
- არ გააუქმო RLS, tenant scope ან validation 403/404/500-ის დასამალად. შეცდომის მიზეზი აღმოფხვერი შესაბამის შრეში.
- simulator-ის, unit-test-ისა და რეალურ მოწყობილობაზე დადასტურების შედეგები ცალ-ცალკე მიუთითე.
- ტექნიკური გამონაკლისი მომხმარებლის ეკრანზე არ გაატანო; გასაგები შეტყობინება და უსაფრთხო correlation ID გამოიყენე.
- როცა ბრაუზერი ხელმისაწვდომია, გაიარე რეალური როლებით desktop/mobile ნაკადები. მიუწვდომელი ბრაუზერის/hardware-ის შემოწმება დასრულებულად არ მონიშნო.

მიღება: PHPStan 0; არსებული ტესტები/Pint/typecheck/build გადის. Zone-ის relation რეალურად გამოიძახე ტესტში.

## ADMIN-01 — სრული ადმინისტრატორი და უფლებების მართვის საფუძველი

ფაილები: `AppServiceProvider.php`, `User.php`, Auth provider, permission seeders, არსებული tenant/membership კოდი.

`admin@protect.ge`-ს მოთხოვნილი სრული ადმინისტრატორის წვდომა შეუნარჩუნე უსაფრთხო migration/bootstrap პროცესით. გადაწყვეტილება email-ის ტექსტზე აღარ იყოს დამოკიდებული; გამოიყენე არსებული RBAC-ის შესაბამისი explicit platform-admin მინიჭება. ელფოსტის შეცვლამ პრივილეგია არ უნდა გადასცეს სხვას ან შემთხვევით გააქროს. პრივილეგირებული ანგარიშისთვის მოითხოვე MFA; business invariant-ები, როგორიცაა არასწორი თანხა ან სხვა კომპანიის ჩანაწერის შეუთავსებლობა, admin შემთხვევაშიც ძალაში რჩება.

განასხვავე platform admin და კომპანიის owner/admin. ყველა ჩანაწერის ოპერაციას ჰქონდეს მკაფიო ორგანიზაციის/კომპანიის კონტექსტი; ნებისმიერი გამონაკლისი იყოს მიზნობრივი და audit-ით.

მიღება: bootstrap admin ყველა ნებადართულ მოდულს ხედავს; ჩვეულებრივი მომხმარებელი თავისთვის admin როლს ვერ ინიჭებს; როლის შეცვლას აქვს audit; ელფოსტის ცვლილების ტესტი; MFA Gate ვერ უქმდება უნივერსალური `Gate::before(true)`-ით.

## ADMIN-02 — მომხმარებლები, როლები, ფუნქციათა ჯგუფები

დაამატე ერთიანი „ადმინისტრირება“: მომხმარებელთა სია, მოწვევა, თანამშრომელთან კავშირი, აქტიურობა, როლები, company/project/team scope და მიმდინარე ეფექტური უფლებები. მოარგე არსებული 11 საწყისი როლი და შექმენი ორგანიზაციისთვის მორგებადი როლების მართვა.

ფუნქციათა ჯგუფები: კომპანიები/პროექტები, თანამშრომლები, დავალებები/ჟურნალი, დასწრება/ტაბელები, ფინანსები, კონტრაქტორები, აქტივები, ანგარიშები/ინტეგრაციები, ადმინისტრირება. თითოეულს ჰქონდეს ქმედებები და საჭირო მგრძნობიარე ველების უფლებები.

მომხმარებლისთვის ფუნქციის გამორთვა რეალურად უნდა იმოქმედოს როლიდან მიღებულ ნებართვაზეც. გაწერე მემკვიდრეობის წესი; თუ საჭიროა explicit deny override, ეს ყველა Gate/query/UI-ში ერთნაირად უნდა შეფასდეს. არ დაამატო მხოლოდ frontend checkbox. მოდულის ორგანიზაციის დონეზე ჩართვა და მომხმარებლის უფლება ცალ-ცალკე ცნებებია.

მიღება: admin რთავს/თიშავს ფუნქციას, მომხმარებელი ცვლილებას ხედავს მომდევნო მოთხოვნაზე, პირდაპირ endpoint-ზეც იგივე შეზღუდვა მოქმედებს. ნაჩვენებია, რომელი როლი/გამონაკლისი აძლევს უფლებას. ბოლო ადმინისტრატორის გაუთვალისწინებელი გაუქმება კონტროლდება.

## TENANT-01 — კომპანიები და ობიექტები

გადაამოწმე Company → Site/Project → Employee/Device/ფინანსური ჩანაწერების კუთვნილება. CurrentCompany მარტო სტატიკურ ცვლადად არ დარჩეს; სერვერზე დადასტურდეს წევრობა და მონაცემების შესაბამისობა. არსებული Site მოდელი გამოიყენე და core domain-ში საჭირო გადაადგილება თავსებადი გზით გააკეთე.

მიღება: სხვა კომპანიის employee/device/project ID ვერ მიებმება არასწორ კომპანიას request-ის შეცვლით; კომპანიის გადართვა სერვერზე მოწმდება; migration-ის შემდეგ ძველი ჩანაწერები შენარჩუნებულია, დაუდგენელი company mapping ცალკე მოსაგვარებელ სიაშია.

## BIO-01 — მკაფიო read-only BioStar ინტეგრაცია

ფაილები: `services/device-connector/src/adapters/suprema-device-gateway.js`, connector index/client, Devices provider/config, credential actions/controller/UI.

კლასის G-SDK სახელის მიუხედავად მოქმედი Node კოდი BioStar REST-ს იყენებს. დაარქვი გასაგები სახელი თავსებადობის შენარჩუნებით და განაახლე docs/config. პირველი ვერსია მხოლოდ კითხულობს BioStar-ის მოწყობილობებს, მომხმარებლების/ბარათების საჭირო მეტამონაცემებსა და მოვლენებს.

სერვერზე გამორთე write dispatch ამ რეჟიმში: `add_user`, revoke, schedule/group sync და remote open რეალურ BioStar-ზე არ გაიგზავნოს. მხოლოდ UI ღილაკების დამალვა საკმარისი არაა. არსებული pending commands/history არ წაშალო; აჩვენე მათი მდგომარეობა და მართვის პასუხისმგებლობა. მომხმარებელმა ნათლად დაინახოს: „ბარათები და დაშვება იმართება BioStar-ში“.

გათავისუფლებაზე CRM-ის მომხმარებელი იბლოკება; BioStar-ის ბარათის გაუქმება გახდეს პასუხისმგებელი ოპერატორის სამუშაო, სანამ დადასტურებული write ინტეგრაცია არ არსებობს. არ აჩვენო „ბარათი გაუქმებულია მოწყობილობაზე“ მხოლოდ CRM ჩანაწერის ცვლილებით.

მიღება: read-only რეჟიმის ტესტში ყველა hardware write უარყოფილია გარე HTTP მოთხოვნის გარეშე; ისტორიული commands შენარჩუნებულია; ეკრანზე სისტემების პასუხისმგებლობა გასაგებია.

## TIMESHEET-EMAIL-01 — სათითაოდ ელფოსტით გაგზავნა

აუცილებელი მოთხოვნა. ტაბელის Show-ზე დაამატე „ელფოსტით გაგზავნა“ უფლების მქონე მომხმარებლისთვის. მოდალში აჩვენე ტაბელი/პერიოდი/სტატუსი, დოკუმენტის preview, მიმღები, სათაური და სურვილისამებრ ტექსტი. ნაგულისხმევი attachment — ქართული PDF.

ტაბელის წაკითხვა არ ნიშნავს ელფოსტით გადაგზავნის უფლებას. დაამატე არსებული namespace-ის შესაბამისი view/export/send permissions და, საჭიროებისას, financial fields/external recipient უფლება. იგივე request ID-ის განმეორება ახალ წერილს არ ქმნის. განზრახ ხელახალი გაგზავნა ცალკე მოთხოვნაა, წინა წერილთან კავშირით. გაგზავნილი დოკუმენტის ვერსია შემდგომი ტაბელის ცვლილებით არ შეიცვალოს.

## TIMESHEET-EMAIL-02 — ერთად / ჯგუფურად გაგზავნა

რიგი: FIX-01/FIX-02 → ADMIN-01/TENANT-01 და MONEY-01/ATT-01 → BIO/QUEUE ჯაჭვი → ADMIN-02/WORKER/FILES → TIMESHEET export და ორივე EMAIL დავალება → JOURNAL/PROJECT → ASSETS/NOTIFY/PWA → OPS. საჭირო დამოკიდებულებები პირველ რიგში დაასრულე; UX-ისა და backend-ის კონტრაქტები წინასწარ დააფიქსირე.

ყოველი ბილეთის დასრულებისას მიუთითე: რა trigger-ზე რა იცვლება, ფაილები/migration-ები, ტესტის შედეგი, რა შემოწმდა ბრაუზერში/მოწყობილობაზე და რა დარჩა. End-to-end მიღების სცენარი იყოს: BioStar event → სწორი თანამშრომელი → დასწრება → დამტკიცებული ტაბელი → ერთი ან ჯგუფური email → გაგზავნის ისტორია. პარალელური სამუშაო სცენარი: მუშაკი იღებს დავალებას → ფოტო → submission → მენეჯერის acceptance → პროექტის პროგრესი.

საბოლოო დასრულება არ ნიშნავს მხოლოდ build-ის წარმატებას: მომხმარებლის მოთხოვნილი ღილაკი უნდა აკეთებდეს რეალურ ოპერაციას, უფლებები უნდა მუშაობდეს ჩვეულებრივი ანგარიშებითაც და შედეგი უნდა მოწმდებოდეს ისტორიაში.
