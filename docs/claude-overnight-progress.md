Fixed by explicitly invoking the Kernel's `syncMiddlewareToRouter()` (via reflection, since it's protected) at the end of `insertMiddlewareAfter()` itself, rather than continuing to depend on an unrelated method call's side effect for correctness. Re-ran the full `php artisan test` suite immediately after this fix (247 passed / 2 skipped, no change from before) — the bug was real but invisible to every existing test, since none of them exercise the real Kernel→Router middleware-group sync path that only matters for actual HTTP requests through the full pipeline.

## Completed: ADMIN-01 (durable platform-admin grant)

**Status:** done, verified live against the real dev DB and running server.

**Root cause (audit A1, confirmed):** `AppServiceProvider::boot()`'s `Gate::before` returned `true` for ANY ability whenever `$user->email === 'admin@protect.ge'` — literal string comparison, not a durable identity. Consequences: (1) changing that account's email would silently drop all access; (2) any other account that later took that exact email string would silently inherit full platform access; (3) `Gate::before` returning `true` unconditionally short-circuits ALL ability checks including `Gate::define('access-financial-data', ...)` (`app/Providers/Auth/AuthModuleServiceProvider.php`), which is supposed to require confirmed 2FA before financial data is reachable — the admin account was silently bypassing that MFA requirement too.

**What was done:**
- New migration `2026_09_21_090000_add_platform_admin_to_users_table.php`: additive `users.is_platform_admin` boolean (default false), with a one-time data backfill setting it `true` for whatever row currently has `email = 'admin@protect.ge'`. Applied to the real dev DB (`php artisan migrate --force`) and verified: `admin@protect.ge` → `is_platform_admin=true`, exactly 1 platform admin total.
- `app/Models/User.php`: added `is_platform_admin` to casts and the property docblock; explicitly **not** added to the `#[Fillable(...)]` list, with a comment explaining why (must only ever be set by the new Action below, never mass assignment).
- `app/Providers/AppServiceProvider.php`: `Gate::before` now checks `$user->is_platform_admin` (id-keyed, not email-keyed) and takes the ability name as a second argument so it can explicitly exclude `access-financial-data` from the bypass — a platform admin still has to complete 2FA to reach financial data, same as anyone else.
- New `app/Domain/Auth/Actions/{GrantPlatformAdminAction,RevokePlatformAdminAction}.php`: the only legitimate way to change the column. Both require the acting user to already be a platform admin (throws `AuthorizationException` otherwise) and write an `AuditLogger` entry (`auth.platform_admin.granted`/`.revoked`). **Real bug found (confirmed empirically, not just by reading code):** `App\Console\Commands\RelayOutboxEvents` and `App\Jobs\Shared\ProcessOutboxEventJob` both used `OutboxEvent::withoutTenantScope()` (the Eloquent-layer scope) and assumed that was sufficient for their inherently cross-tenant role — but `outbox_events` also carries a real Postgres RLS policy (`organization_id = current_setting('app.current_org_id')`), and neither the relay nor the job ever set that GUC *before* their first read. Under a real restricted role (not a superuser, per the standing constraint), this means: `RelayOutboxEvents` would see **zero** rows from **any** tenant, always — the relay would silently never dispatch anything in production. Verified this precisely with a small standalone reproduction script against the real `pgsql_rls_test` database before writing the fix (not assumed from reading the policy SQL alone): a plain `SELECT` with no org context returns 0 rows, confirming the bug.

**The harder half of the bug, found while fixing it:** even after adding a narrow, `app.outbox_relay_active`-gated `FOR SELECT` policy to let the relay/job see rows across tenants, `ProcessOutboxEventJob::handle()`'s `SELECT ... FOR UPDATE` (needed for its idempotency row-lock) still returned nothing — **empirically confirmed** that Postgres does NOT honor a `FOR SELECT`-only policy for a locking read; it requires a policy applicable to `UPDATE`. Fixed by adding a second, `FOR UPDATE`-classified policy gated on the same flag but with an explicit `WITH CHECK (false)` — this makes the flag able to make a row *visible/lockable* across tenants, but structurally unable to ever authorize the row's actual write (Postgres ORs multiple permissive policies' `USING` and `WITH CHECK` independently; the real write still only succeeds via the existing `outbox_events_tenant_isolation` policy's own `WITH CHECK`, i.e. only once `app.current_org_id` has been narrowed to that row's real tenant). This is recorded here specifically because it contradicted my own first assumption about how Postgres RLS interacts with row-locking reads — worth remembering for any future RLS-adjacent work in this codebase.

**What was done:**
- New migration: two additive RLS policies on `outbox_events` — `outbox_events_system_relay_select` (`FOR SELECT`) and `outbox_events_system_relay_lock` (`FOR UPDATE`, `WITH CHECK (false)`), both gated on a distinct `app.outbox_relay_active` GUC that no web request/controller/user-input path anywhere in this codebase ever sets — only the relay/job's own trusted server-side code, always `is_local=true` (transaction-scoped, can't leak to another statement/job on a reused worker connection). **Not** a BYPASSRLS/superuser grant to `oda_app` — the standing constraint's ban on that stays intact; every other RLS-protected table is completely unaffected, and this table's OWN existing tenant policy is unaffected too — this is purely additive.
- `RelayOutboxEvents::handle()`: wraps the flag-set + read in one `DB::transaction()` (`is_local=true` only has effect for the statement's own transaction — a bare, unwrapped statement is its own auto-committed transaction in Postgres, so the flag would have reverted before the very next statement without this).
- `ProcessOutboxEventJob::handle()`: two-phase pattern — briefly set the relay flag, locate+lock the row by id, then IMMEDIATELY clear the flag and set `app.current_org_id` to that row's real tenant before dispatching `OutboxEventReady` or writing `processed_at` — the cross-tenant escape hatch is only ever open for the single statement that needs it.

**Documented precedence, most authoritative first:** (1) an explicit deny-override always wins, even over a platform admin; (2) a direct grant-override; (3) a role-derived permission (the baseline); (4) ADMIN-01's platform-admin `Gate::before` bypass, unchanged, for everything else.

**The hard part, and a real, non-obvious finding worth remembering for any future Gate/spatie work in this codebase:** the first implementation attempt registered the deny-check as a plain `Gate::before` in `App\Providers\AppServiceProvider::boot()`, placed as the very first statement — textually before even ADMIN-01's platform-admin callback — on the reasonable assumption that Laravel's Gate runs `beforeCallbacks` in registration order and returns the first non-null result (true, and verified by reading `Illuminate\Auth\Access\Gate::raw()`/`callBeforeCallbacks()` directly). **This did not work — proved by a failing regression test, not assumed working.** Root cause, found by adding a temporary file-write inside the closure and observing it never fired for the failing case: `spatie/laravel-permission`'s `PermissionRegistrar::registerPermissions()` registers its **own** `Gate::before` (`vendor/spatie/laravel-permission/src/PermissionRegistrar.php`), wired up via `callAfterResolving(Gate::class, ...)` — a callback that fires the moment `Gate::class` is *first resolved* from the container. Since **any** `Gate::before(...)` facade call is itself what triggers that first resolution, spatie's `afterResolving` callback fires *during* that resolution — before the facade's own `->before($myClosure)` call actually appends anything — meaning spatie's permission-check callback always ends up *first* in the array, regardless of source-code order. It returns `true` immediately the moment a role/direct grant provides the permission, short-circuiting `Gate::raw()` before any app-level `Gate::before` (including ADMIN-01's, and the new deny-check) ever runs.
**The actual fix:** override `App\Models\User::hasPermissionTo()` — the exact method spatie's own `Gate::before` calls internally (via `checkPermissionTo()`, which just wraps it in a try/catch) — to consult the deny-list *first* and return `false` immediately if denied, before delegating to spatie's own logic (aliased via `HasRoles::hasPermissionTo as private spatieHasPermissionTo` in `User`'s trait-use block, since `parent::` cannot reach a trait method). This works regardless of `Gate::before` registration order, because it intercepts at the exact place spatie itself queries. The app-level `Gate::before` in `AppServiceProvider` is kept as a second layer specifically for an ability that isn't a registered permission name at all (so spatie's callback has nothing to grant and defers to `null`) — needed so a deny still beats the platform-admin bypass in that case too. A second, smaller bug found and fixed during the same debugging pass: the per-process denial-name memoization cache (`App\Domain\Auth\Support\PermissionDenialCache`, added for performance — many ability checks can happen in one request) must be explicitly busted by both `DenyUserPermissionAction` and `RemoveUserPermissionDenialAction` immediately after their write, or a `can()` check made earlier in the same request/process (e.g. in a test, or a queue worker reusing a process) would read a stale pre-mutation list.

**Three real correctness bugs found and fixed while writing this ticket's own tests — not guessed, not theoretical:**
1. **Dispatch-inside-transaction hazard:** the first draft dispatched `SendTimesheetEmailJob` from *inside* the same `DB::transaction()` that created the delivery row. Under `QUEUE_CONNECTION=sync` (this codebase's own test environment, `phpunit.xml`) that job runs synchronously mid-transaction — so when it failed and tried to record `status='failed'`, that write got rolled back along with everything else the instant the exception propagated, silently destroying the very failure record the job existed to create. Fixed by moving both `send()`'s and `retry()`'s job dispatch to run only after their respective transaction closures return (never before commit) — this also protects a real async deployment against a worker picking the row up before the creating transaction has actually committed.
2. **A queued Mailable silently defeats its own queued Job wrapper:** `TimesheetSnapshotMail` originally implemented `ShouldQueue`. `Illuminate\Mail\PendingMail::send()` redirects any `ShouldQueue` mailable straight to `queue()` instead of actually sending — so `SendTimesheetEmailJob::handle()`'s `Mail::to(...)->send(...)` call was merely re-queuing the mail (never touching the transport) and then immediately, wrongly, marking the delivery `sent`. Caught by `Mail::assertSent()` failing with "did you mean assertQueued()?" — a real, load-bearing test failure, not a flaky one. Fixed by removing `ShouldQueue` from the Mailable: `SendTimesheetEmailJob` is itself the already-queued unit of work; the Mailable it builds must run synchronously inside that job.
3. **Context-clearing wiped the caller's own tenant scope:** `SendTimesheetEmailJob::handle()`'s `finally` block unconditionally called `CurrentOrganization::clear()` — correct for a real async worker (which starts with no ambient context) but wrong under `QUEUE_CONNECTION=sync`, where the job runs synchronously inside whatever request/test already had its own `CurrentOrganization` set; clearing silently wiped that caller's tenant context for the rest of the same request/test. Fixed to save the value on entry and restore it (not unconditionally clear) in `finally`.
